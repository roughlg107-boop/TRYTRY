- **frontend**：部署於 Firebase Hosting，使用者認證使用 Firebase Auth。  
- **backend**：部署於 Render，所有敏感設定（如 OpenAI API Key）使用環境變數。  
- **shared**：可透過 npm workspace 或複製/匯入方式供 frontend、backend 使用，僅放「結構與常數」，不放邏輯。

## 二、系統模組拆分說明

系統依「使用流程階段」與「職責邊界」拆成以下模組。每個模組都有明確的「嚴格不能做的事」以符合「AI 不決策、不自由發揮」原則。

---

### 2.1 前端模組

| 模組 | 職責 | 嚴格不能做的事 |
|------|------|----------------|
| **輸入／上傳** | 接收「第一次拜訪報告」文字或檔案；可選接收「過往成功簡報」檔案。驗證格式、大小後送交後端。 | 不解析報告或簡報的「策略意涵」；不替使用者選擇要填哪個範本；不自動改寫或摘要使用者上傳的內容。 |
| **流程導引** | 依步驟 1→2→3→4 導引使用者，顯示目前階段、必填/選填、錯誤或缺漏提示。 | 不自動跳過步驟；不代替使用者點選「範本」或「確認」；不隱藏「範本建議清單」而直接產出簡報。 |
| **範本選擇** | 顯示後端回傳的「簡報範本建議清單（2～3 個）」，讓使用者點選其一。僅將使用者選擇的範本 ID 傳給後端。 | 不自動選定範本；不新增、刪除或改寫清單項目；不在未選擇時呼叫「產出最終簡報」API。 |
| **結果展示** | 顯示後端回傳的「最終簡報文字」（固定頁數、頁序、每頁角色）。可支援匯出或複製。 | 不重新排序頁面、不合併/刪除頁、不改寫內容；不替內容做「策略建議」或額外說明。 |
| **認證與儲存** | Firebase Auth 登入/登出；必要時將「使用者選擇的範本 ID、專案識別」等交給後端或 Firestore。 | 不在前端存放或處理 API Key；不決定「哪些資料要存到 Firestore」（由後端或既定規格決定）。 |

---

### 2.2 後端模組

| 模組 | 職責 | 嚴格不能做的事 |
|------|------|----------------|
| **拜訪報告處理** | 接收第一次拜訪報告，進行「資訊抽取」與「缺漏標示」；回傳結構化欄位與缺漏項，不給策略建議。 | 不產出策略建議、不推薦範本、不撰寫簡報內文；不合併或改寫使用者原文；不自行決定「哪些欄位必填」。 |
| **過往簡報解析** | 若使用者上傳過往成功簡報，僅做「結構解析」（如頁數、每頁標題/角色、段落結構）；回傳結構描述。 | 不摘要、不合併頁面、不重寫內容；不依此結構自動產生新簡報；不從內容推論「策略」或「建議範本」。 |
| **範本建議** | 依既有規則（如排除不適用條件）產出「2～3 個候選範本」清單；回傳 ID 與顯示用名稱等。 | 不替使用者選定單一範本；不產出最終簡報；不新增或修改範本定義；不依「策略判斷」決定清單內容（僅排除不適合）。 |
| **最終簡報產出** | 依「使用者已選定的範本 ID」與既有模板（固定頁數、頁序、每頁功能角色），在模板中填入內容，回傳最終簡報文字。 | 不改變頁數、頁序或每頁角色；不自由創作新頁或新結構；不替使用者選擇其他範本；不加入未在模板中定義的欄位或建議。 |
| **儲存與識別** | 與 Firebase Firestore 互動：存使用者輸入、解析結果、選定範本、生成結果等；提供專案/使用者識別。 | 不儲存 API Key 或密碼於 Firestore；不依儲存內容做策略或範本決策；不暴露其他使用者的資料。 |

---

### 2.3 共用（shared）模組

| 模組 | 職責 | 嚴格不能做的事 |
|------|------|----------------|
| **型別／介面** | 定義 API 請求/回應形狀、拜訪報告欄位、簡報結構描述、範本 ID 等 TypeScript 型別或介面。 | 不包含任何 API 呼叫、不包含 AI prompt、不包含「若…則建議…」等商業邏輯。 |
| **常數** | 定義範本 ID 枚舉、API 路徑常數、錯誤碼等前後端一致的值。 | 不包含秘密或環境變數實際值；不包含可執行的業務規則（僅為識別用常數）。 |

---

### 2.4 AI 呼叫邊界（後端內）

- **呼叫時機**：僅在後端「拜訪報告處理」「過往簡報解析」「範本建議」「最終簡報產出」等服務中，依既定規格呼叫 OpenAI。
- **嚴格不能做**：  
  - 不讓 AI 輸出「請選擇範本 A」等決策型結論給使用者作為最終選擇；  
  - 不讓 AI 自由決定簡報頁數、頁序或新增頁面；  
  - 不讓 AI 在模板外創作新結構或策略建議。  
- 本步驟不實作 prompt 或 schema，僅定義：**AI 僅在既定模板中填入內容，且範本選擇權必在使用者。**

## 三、API 與前端之間的資料流示意（文字描述）

1. **步驟 1 — 輸入第一次拜訪報告**  
   - 前端：使用者輸入或上傳報告 → 前端驗證格式/大小 → 呼叫後端「拜訪報告處理」API，送出報告內容（及可選的專案/使用者識別）。  
   - 後端：僅做資訊抽取與缺漏標示，回傳結構化欄位 + 缺漏項清單（不包含策略或範本建議）。  
   - 前端：顯示抽取結果與缺漏標示，供使用者檢視或補齊；不自動進入步驟 2。

2. **步驟 2（可選）— 上傳過往成功簡報**  
   - 前端：使用者上傳檔案 → 呼叫後端「過往簡報解析」API。  
   - 後端：僅做結構解析，回傳頁數、每頁標題/角色、段落結構等（不摘要、不合併、不重寫）。  
   - 前端：可顯示解析出的結構供參考；此步驟可略過。

3. **步驟 3 — 範本建議與使用者選擇**  
   - 前端：使用者點選「取得範本建議」後，將步驟 1（及可選的步驟 2）的結果傳給後端「範本建議」API。  
   - 後端：依規則排除不適合範本，回傳 2～3 個候選範本（ID + 顯示名稱等）。  
   - 前端：顯示清單，**由使用者點選一個範本**；將使用者選定的範本 ID 記住，供步驟 4 使用。  
   - 未選擇前，前端不呼叫「產出最終簡報」API。

4. **步驟 4 — 產出最終簡報**  
   - 前端：使用者確認後，以「步驟 1 的報告（及可選的步驟 2 結構）」+ **使用者已選定的範本 ID** 呼叫後端「最終簡報產出」API。  
   - 後端：依該範本（固定頁數、頁序、每頁角色）在模板中填入內容，回傳最終簡報文字。  
   - 前端：展示結果，可支援複製或匯出；不改寫、不重排頁面。

5. **貫穿流程**  
   - 認證：前端透過 Firebase Auth 取得 token，呼叫後端時於 Header 帶入；後端可選擇驗證 token 或委由 Firebase Admin 驗證。  
   - 儲存：後端在適當時機將輸入、解析結果、選定範本、生成結果寫入 Firestore（依設計規格）；前端不直接寫入 Firestore 業務資料，僅讀取後端允許的資料（若有設計查詢 API）。

以上為 STEP 0 之完整產出：專案資料夾結構、系統模組拆分、各模組「嚴格不能做的事」、以及 API 與前端之間的資料流描述。**未包含任何 AI prompt、JSON schema 或商業邏輯實作**，可依此進行下一步開發指示。
